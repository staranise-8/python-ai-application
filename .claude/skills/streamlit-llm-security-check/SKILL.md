# Streamlit + LLM アプリのセキュリティチェック

Streamlit と LLM API を使ったアプリを調べ、**問題点を重大度つきのセキュリティレポートにまとめる**スキル。

## このスキルの前提

- **報告だけを行い、コードや設定ファイルは変更しない。** ユーザーは修正するかどうかを自分で決めたいので、修正案はレポートの中にコード例として書くだけにする。レポートのファイルを書き出すのは問題ない。
- **秘密情報の値を絶対に表示しない。** `.env` や `secrets.toml` を `cat` や Read でそのまま開くと、APIキーが会話のログに残ってしまう。キーがあるかどうかの確認には、同梱の `scripts/scan.py` を使う（値を伏せ字にして表示する）。レポートにキーの値を書くときも、`AIza…(39文字)` のように先頭数文字だけにする。
- **実際にある問題だけを書く。** 「念のため」の指摘を並べるとレポートが読まれなくなる。指摘するのは、コードで実際に確かめた箇所（`file:line`）と、具体的な悪用シナリオが書けるものだけにする。確信が持てないものは「要確認」と明記して分ける。
- **重大度は利用環境によって変わる。** 同じ問題でも、自分の PC（localhost）で自分だけが使う場合と、インターネットに公開する場合では危険度が大きく違う。各指摘には「ローカル利用時」と「公開時」の2つの重大度を付ける。ユーザーが公開予定を話していれば、その前提をレポートの冒頭に書く。

## 手順

### 1. アプリの全体像をつかむ

- Python ファイル・`requirements.txt` / `pyproject.toml`・`.gitignore`・`.streamlit/`（`config.toml`、`secrets.toml` があるか）・`Dockerfile` など、デプロイ関連のファイルを一覧にする。`.venv` や `node_modules` などは除外する。
- 次の点を把握する。
  - 使っている LLM SDK（`google-genai`、`openai`、`anthropic`、`langchain` など）
  - APIキーの読み込み元（環境変数、`st.secrets`、画面での入力）
  - ユーザーが入力できるもの（テキスト、ファイルアップロード、URL）
  - LLM の出力をどう使っているか（表示するだけか、コード実行・ファイル操作・外部への通信・ツール呼び出しに使っているか）
- README や CLAUDE.md があれば読み、公開する予定かどうかを確認する。

### 2. 自動スキャンを実行する

```bash
python <このスキルのディレクトリ>/scripts/scan.py <チェック対象のディレクトリ>
```

このスクリプトは次の項目を一覧にする。

- APIキーらしき文字列（伏せ字で表示）
- 危険になりうる書き方（`unsafe_allow_html`、`eval`、`subprocess`、`st.cache_*`、`type="password"` など）がある箇所
- `.gitignore` に `.env` や `secrets.toml` が入っているか
- バージョンが固定されていない依存パッケージ
- LLM 呼び出しに出力トークンの上限が付いているか

スキャン結果は**調べる候補の一覧**であって、そのまま指摘にしてはいけない。各候補は該当するコードを読み、本当に問題かどうかを判断する。たとえば `.env` の中にキーがあるのは正常で、問題になるのはそれが git で追跡されている場合や、コードに直接書かれている場合だけ。

### 3. チェックリストに沿って手で確認する

`references/checklist.md` を読み、カテゴリごとに確認する。特に次の3つは、Streamlit 特有で見落としやすい。

1. **ウィジェットの値はブラウザに送られる。** `st.text_input(value=サーバー側のAPIキー, type="password")` と書くと、伏せ字で表示されていても、キーそのものがブラウザに届く。アプリを公開すると、アクセスした誰でもキーを取り出せる。
2. **`st.cache_data` / `st.cache_resource` やモジュールレベルの変数は、全ユーザーで共有される。** ユーザーごとのデータ（入力内容、生成結果、ユーザーが入力したAPIキーを使うクライアント）をここに入れると、他のユーザーに漏れる。
3. **認証がないまま公開すると、あなたのAPIキーを誰でも使える。** その結果、請求額が膨らんだり、利用制限に達したりする。

git リポジトリであれば、次のコマンドも実行する。

- `git ls-files` で、`.env` や `secrets.toml` が追跡されていないかを確認する。
- `git log --all --oneline -S "AIza"` のように、キーの形式で過去のコミットを検索する。出力にキーの値を出さないよう、`-p` は付けない。

依存パッケージについては、`pip-audit` が使える環境なら実行する。インストールされていなければ、勝手に入れずに、レポートの中で実行方法を案内する。CVE 番号は、ツールの出力で確認できたものだけを書き、記憶に頼って書かない。

### 4. レポートを書く

レポートはプロジェクトのルートに `security-report-YYYYMMDD.md` として保存する。会話には、重大度ごとの件数と、上位3件の要点だけを短く返す。

## 重大度の基準

| 重大度 | 目安 |
|---|---|
| 🔴 Critical | すぐに悪用でき、被害が大きい（キーがコードや git 履歴に含まれている、LLM の出力を `exec` している、など） |
| 🟠 High | 条件がそろえば大きな被害につながる（公開時にキーがブラウザへ渡る、認証なしで公開している、ユーザー間でデータが混ざる、など） |
| 🟡 Medium | 被害が限定的、または悪用に手間がかかる（エラー詳細の表示、入力サイズの上限がない、など） |
| 🔵 Low | 多層防御のための改善（バージョン固定、トークン上限の指定、など） |
| ⚪ Info | 問題ではないが知っておくとよいこと（OneDrive などのクラウド同期フォルダーに `.env` がある、など） |

## レポートの形式

必ず次のテンプレートに沿って書く。読み手はコードを書いた本人なので、専門用語には短い説明を付け、「何が起こりうるか」を具体的に書く。

```markdown
# セキュリティレポート: <アプリ名>

- 実施日: YYYY-MM-DD
- 対象: <ディレクトリ>（主なファイル: ...）
- 構成: Streamlit <バージョン> / <LLM SDK> / APIキーの読み込み元: ...
- 前提: <ローカル利用のみ / 公開予定 / 不明（両方の重大度を記載）>
- 範囲: アプリのコード、秘密情報の管理、依存パッケージ、デプロイ設定（このレポートは確認結果の報告だけで、コードは変更していません）

## サマリー

| 重大度 | ローカル利用時 | 公開時 |
|---|---|---|
| 🔴 Critical | n | n |
| 🟠 High | n | n |
| ...

<2〜3文の総評。最優先で対応すべき点>

## 指摘事項

### [S-01] <短いタイトル>
- **重大度**: ローカル 🔵 Low / 公開時 🟠 High
- **場所**: `app.py:70`
- **内容**: 何が問題か（該当コードを数行引用する。秘密情報は伏せ字にする）
- **起こりうること**: 具体的な悪用シナリオ
- **修正案**:
  ```python
  # 修正例
  ```
- **参考**: OWASP LLM Top 10 の該当項目など（あれば）

（以下、重大度の高い順）

## 要確認事項
コードだけでは判断できなかった点と、確認する方法。

## 問題がなかった項目
確認して問題がなかった観点を箇条書きで書く（例: `unsafe_allow_html` は不使用、LLM の出力をコード実行に使っていない）。どこまで確認したかを読み手に伝えるため、省略しない。

## 推奨する次のステップ
優先順位つきで3〜5項目。
```

指摘がない重大度の区分は、サマリーの表で 0 件とするだけでよい。指摘事項の欄に空の見出しを作らないこと。
